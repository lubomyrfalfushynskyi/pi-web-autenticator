# Наскрізне встановлення 2FA та суміжних входів

Це головна карта порядку встановлення для `pi-site-backend-2fa-module`,
`avtor-cc338-module` і сайту InTrack. У кожній окремій інструкції має бути
посилання сюди та номер її етапу.

## Межі системи

```text
privacyIDEA + серверний токен-плагін (етап 1)
        ↓
користувач / realm / resolver / token serial (етап 2)
        ↓
backend сайта + цей npm-модуль (етап 3)
        ↓ лише для CC338
локальний агент підпису + доступний носій (етап 4)
        ↓
приймальні тести (етап 6)

Доменний SSO сайта — окрема суміжна гілка (етап 5).
Вхід у Windows/Linux OS через Credential Provider/PAM — інша гілка
avtor-cc338-module і не є умовою браузерної 2FA (етап 7).
```

OTP не вимагає локального агента. Для challenge-response браузер не
спілкується з privacyIDEA безпосередньо: backend сайта зберігає операцію й
підтверджує результат, агент лише підписує виклик локальним ключем.

## Глобальні передумови

- Визначені сайт і середовище (тестове/робоче), DNS/TLS та доступність
  серверів між собою.
- Узгоджені ідентифікатори: site user, PI resolver/UID, realm і token serial.
- Секрети доступу та PIN зберігаються лише у відповідному локальному
  сховищі/секретному конфігу; не вставляються в браузер, документацію чи
  команди, що потрапляють у журнал.
- Зміни проводяться від етапу 1 до 6. Етапи 5 і 7 підключаються лише якщо
  потрібні доменний SSO або інтерактивний вхід у саму ОС.

## Етап 1 — privacyIDEA і серверний тип токена

**Модуль:** privacyIDEA та серверна частина
[`avtor-cc338-module`](../../avtor-cc338-module/README.uk.md) (суміжний каталог
у Desktop/projects; якщо репозиторії розташовані окремо, відкрийте його README.uk.md).

**Потрібно до початку:** сервер privacyIDEA встановлений і адміністратор має
доступ; відома версія PI та сумісна схема розгортання (Docker чи native).
Токен-плагін ще не має бути увімкнений у продуктивному потоці, доки не
пройдуть його перевірки.

**Зробити:** вибрати одну інструкцію розгортання PI, додати серверний
`avtorcc338` token class і перевірити реєстрацію типу/виклик за відповідною
інструкцією репозиторію. Для `pkcs11cr` потрібен його окремий сумісний
серверний модуль; цей репозиторій його не встановлює.

**Очікувано після:** PI доступний сайту по TLS; вибраний token type
зареєстрований; тестовий запит проходить; помилки/журнали не розкривають PIN
чи API-ключ.

**Далі:** етап 2. Не переходити до сайту, доки PI не бачить token type.

**Troubleshooting:**

- Token type відсутній після інсталяції — перевірити шлях саме до Python
  environment privacyIDEA, права на файл, список модулів токенів і журнали
  сервісу; перезапускати тільки після перевірки конфігурації.
- Після перезапуску PI падає — повернути збережений конфіг/файл модуля,
  перевірити сумісність із фактичною версією privacyIDEA та traceback.
- Сайт не дістає PI — перевірити DNS, маршрут, TLS chain/hostname, порт і
  дозволений API endpoint; не вимикати перевірку TLS як постійне виправлення.
- Вибір Docker/native невідомий — не запускати обидва сценарії; звірити
  [`deployment/README.md`](../../avtor-cc338-module/deployment/README.md).

## Етап 2 — користувачі, enrollment і серверні зіставлення

**Власник:** privacyIDEA та адмінка цільового сайту; сайтова бібліотека не
створює користувачів і не прив’язує токени.

**Потрібно до початку:** етап 1 пройшов; адміністратор знає PI realm і
resolver; тестовий користувач сайту існує.

**Зробити:** створити/перевірити PI user; enrollment токена виконати штатним
способом для обраного профілю; зіставити site account із PI user, realm,
resolver/UID і точним serial. Для OTP зберегти тип стандартного
validation-токена. Для CC338/P11 challenge-response звірити профіль і
сертифікатний ключ із token serial. Domain UID не замінювати лише логіном,
якщо інтеграція вимагає стійкого зіставлення.

**Очікувано після:** контрольний lookup повертає саме очікуваного PI user та
serial; тестовий фактор відхиляє неправильний код/підпис.

**Далі:** етап 3.

**Troubleshooting:**

- `UNKNOWN_USER` — realm/resolver/UID не збігаються; це не помилка коду OTP.
- `NO_TOKEN` або `not_linked` — токен не зарахований цьому PI user або сайт
  не має актуального serial mapping.
- Старий CC338 serial після перевипуску — оновити зіставлення після enrollment;
  не перевидавати сайтову сесію за старим pending login.
- OTP постійно відхиляється — перевірити час сервера й authenticator, token
  type та account mapping; не записувати seed у логи/документи.

## Етап 3 — серверний адаптер у сайті

**Модуль:** `pi-site-backend-2fa-module` у backend сайту. Для InTrack
додатковий host guide:
[`InTrack: site-2fa-install.md`](https://github.com/lubomyrfalfushynskyi/InTrack/blob/main/docs/modules/site-2fa-install.md).

**Потрібно до початку:** етапи 1–2 успішні; backend підтримує Node.js 20+;
є серверний PI transport або визначені TLS/API key/timeout правила; є
ізольоване тестове середовище та спосіб відкату archive/package.

**Зробити:** створити versioned npm archive через `npm pack`, додати його в
backend build context сайта, закріпити точний `file:` dependency, виконати
`npm install` і rebuild лише backend. Сайт реалізує HTTP routes, pending
login/expiry, виклик provider, сесію та перевірку returned serial/type.

**Очікувано після:** пакетна версія збігається із закріпленою; валідний фактор
дозволяє сесію лише після серверного `ACCEPT`; неправильний фактор/serial не
створює сесію; браузер не отримує PI URL, API key чи `transaction_id`.

**Далі:** етап 4 для CC338 або одразу етап 6 для OTP.

**Перевірки розробки:** у репозиторії модуля `npm test` і `npm run lint`; у
сайті — його власні тести й health checks. Для InTrack конкретні команди та
поточна версія є у власній інструкції.

**Troubleshooting:**

- Node не знаходить пакет — перевірити назву/версію tgz у `package.json`, чи
  файл лежить у Docker build context, потім перевстановити залежність.
- Контейнер показує стару версію — перевірити image rebuild, правильний
  compose project/container та версію всередині запущеного контейнера.
- `MISCONFIGURED` — перевірити PI API key mode, realm, transport і token
  mapping; не показувати сирі PI відповіді користувачу.
- Backend відмовляє після коректного підпису — звірити pending-login
  `transaction_id`, expiration, serial та token type з серверним mapping.
- API key/transaction ID потрапив у browser response — зупинити тестування,
  усунути витік і очистити/перевипустити відповідний секрет за процедурою
  сайту до продовження.

**Постійна робота в контейнерах:** пакет є частиною backend image, окремого
2FA-контейнера немає. Закріплюйте точний archive і lockfile, включайте tgz у
build context, зберігайте pending login/transaction ID у серверному сховищі
з TTL, переживаючому рестарти (не лише в пам'яті процесу), і після оновлення
перебудовуйте тільки backend. Перевіряйте package version усередині
контейнера, health та позитивний/негативний сценарії. Відкат робіть на
попередню версію archive/lockfile; не видаляйте дані volumes сайту.
У поточному InTrack challenge state поки process-local: рестарт анулює
активний вхід, а MFA через кілька backend replicas не підтримується. Для
інших сайтів це залежить від їхньої реалізації; для HA потрібне shared store
з TTL.

## Етап 4 — клієнтський агент для браузерного CC338

**Модуль:** агент підпису сайту, який постачається/описаний самим сайтом
(для InTrack — `tools/pkcs11cr-agent`, див. його `README.md`). Це не
Credential Provider і не PAM.

**Потрібно до початку:** етапи 1–3 успішні; фізичний носій вставлений у
цільовий клієнт/VM; на цій ОС є сумісний виробничий PKCS#11 driver, PC/SC,
Python і залежності агента; TLS-сертифікат сайту довірений; точний origin
сайту дозволений в конфігурації агента.

**Зробити:** встановити ОС-специфічним інсталятором; налаштувати origin та
шлях до PKCS#11 module; виконати `--check`; запустити агент; PIN вводити
локально тільки у вікні агента. Після сну переініціалізувати носій згідно з
інструкцією токена, не залишати його в активному стані без потреби.

**Очікувано після:** агент доступний лише дозволеному origin, бачить токен і
підписує challenge; сайт перевіряє підпис через PI; сесія створюється тільки
на сайті після `ACCEPT`.

**Troubleshooting:**

- Агент недоступний — перевірити, що запущений правильний user-level service/
  tray process, порт локального агента і CORS/origin allowlist.
- Носій не видно — перевірити USB passthrough у VM, PC/SC reader/service,
  драйвер і PKCS#11 path; не встановлювати драйвер на хост замість VM.
- Після sleep PIN/читач завис — завершити агент, перевставити/переініціалізувати
  порт носія і перезапустити PC/SC та агент у правильному порядку.
- Підпис вибирає не той сертифікат — порівняти `key_hint_kind` і ключову
  підказку профілю з сертифікатами токена та його PI enrollment.
- Windows-інсталятор або vendor DLL не перевірені — позначити сценарій
  `BLOCKED/UNVERIFIED`, не робити висновок за успіхом на Linux.

## Етап 5 — доменний SSO вебсайту (умовний)

Це окрема інтеграція сайту й доменного шлюза. Вона не додається цією npm
бібліотекою і не є умовою OTP/CC338 login через форму.

**Потрібно:** домен/DNS/Kerberos або інший затверджений протокол, gateway,
TLS/mTLS trust, зіставлення доменного UID з обліковим записом сайту,
синхронізований час, перевірений logout і політика повторного входу.

**Очікувано:** SSO підтверджує саме зіставлену особу; logout не створює
нескінченне автоматичне повернення; браузер не може підмінити твердження.

**Troubleshooting:** звірити DNS/SPN/keytab або mTLS chain відповідно до
реалізації, годинники, browser allowlist, gateway health і server-side
identity mapping. Не виправляти проблему SSO послабленням site MFA.

## Етап 6 — приймання веб-2FA

**Потрібно:** етап 3 обов’язковий; етап 4 для CC338; етап 5 лише для SSO.
Мати тестові користувачі та доступний резервний snapshot/backup.

**Зробити:** перевірити позитивний і негативний OTP, challenge-response,
неправильний/повторний/прострочений challenge, мапінг іншого serial,
session/logout, аудит, відсутність секретів у browser responses; повторити
SSO у звичайному доменному браузері окремо від локального входу за межами
домену.

**Очікувано:** за кожним сценарієм записано `PASS`, `FAIL` або `BLOCKED`;
непідключений фізичний носій чи неперевірений Windows driver — `BLOCKED`, не
`PASS`.

**Troubleshooting:** фіксувати час і request correlation ID без секретів,
перевіряти site/backend/PI журнали послідовно; після будь-якого виправлення
повторити саме негативний і позитивний сценарії, які могли змінитися.

## Етап 7 — інтерактивний вхід у Windows/Linux OS (умовний, окремий)

**Модуль:** відповідна частина `avtor-cc338-module` — Windows Credential
Provider чи Linux-клієнт/PAM за їхніми окремими deployment guides. Цей етап
не потрібен, щоб встановити браузерну 2FA на сайті.

**Передумова:** етап 1 і потрібне enrollment завершені; ОС-клієнт, його
серверний протокол, політика входу й recovery-план перевірені на окремій VM.
Credential Provider/PAM змінює критичний шлях логону ОС — не ставити на host
без окремого погодженого сценарію й відновлення.

**Troubleshooting:** користуватися локальними інструкціями відповідної ОС,
перевіряти фактичний стан реєстрації/служб/логів та мати робочий fallback.
Не трактувати успішний OS logon як доказ браузерної site 2FA.

## Коротка діагностика за симптомом

| Симптом | Перевіряти спершу | Етап |
|---|---|---:|
| PI не знає token type | PI module registration, service logs | 1 |
| користувача/токен не знайдено | realm/resolver/UID/serial mapping | 2 |
| сайт показує старий module version | archive pin, build context, backend image | 3 |
| браузер не бачить агента | process/service, origin/CORS, local port | 4 |
| агент не бачить CC338 | VM USB passthrough, PC/SC, PKCS#11 | 4 |
| SSO не працює, але форма входу працює | domain gateway/DNS/time/trust | 5 |
| OS login відмовляє, сайт працює | CP/PAM client and OS-specific logs | 7 |

Не продовжуйте далі за етап, що не пройшов перевірку; усувайте причину на
власному шарі й повторюйте перевірку цього етапу.
